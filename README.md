

# winsock-playground

Пошаговое изучение Winsock2: от простейшего блокирующего эхо-сервера к мультиплексированию
через select(), пулу потоков, асинхронной модели на IOCP и собственному length-prefixed протоколу
поверх TCP.

Платформа: Windows, MSVC, C++17 (04-echo-iocp, 05-echo-iocp-acceptex, 06-echo-refcount,
07-echo-iocp-server и 08-length-prefixed-protocol используют -> C++20).

## Проекты

| Проект                  | Модель ввода-вывода                          | Клиентов одновременно       | Порт |
|-------------------------|----------------------------------------------|-----------------------------|------|
| 01-echo-blocking        | блокирующие вызовы, один поток               | 1 (последовательно)         | 8080 |
| 02-echo-select          | select(), неблокирующие сокеты, один поток   | до FD_SETSIZE (1024)        | 8080 |
| 03-echo-thread-per-client | блокирующие сокеты, поток на клиента       | ограничено ресурсами ОС     | 8080 |
| 04-echo-iocp            | IOCP + WSARecv/WSASend (overlapped)          | тысячи                      | 9000 |
| 05-echo-iocp-acceptex   | IOCP + AcceptEx (полностью асинхронный)      | тысячи                      | 5555 |
| 06-echo-refcount        | IOCP + AcceptEx + счётчик ссылок на Conn     | тысячи                      | 5555 |
| 07-echo-iocp-server     | IOCP + AcceptEx + refcount + graceful shutdown + idle timeout + статистика | тысячи | 5555 |
| 08-length-prefixed-protocol | IOCP + AcceptEx + refcount + framing `[u32 BE len][payload]` | тысячи | 5555 |

## 01-echo-blocking

Базовая схема: `socket` → `bind` → `listen` → `accept` → цикл `recv`/`send`.

- Один клиент обслуживается целиком, остальные ждут в очереди `listen(SOMAXCONN)`.
- Отправка циклом по `curr < n`: учтено, что `send()` может передать меньше запрошенного.
- Адрес клиента печатается через `inet_ntop`, при ошибке подставляется `"?"`.
- Завершение: `shutdown(client, SD_SEND)` перед `closesocket`.

Ограничение модели: пока текущий клиент не отключится, другие не обслуживаются.

## 02-echo-select

Однопоточный мультиплексор на `select()`.

- `FD_SETSIZE` переопределяется до 1024 **до** включения `winsock2.h`.
- Все сокеты, включая слушающий, переводятся в неблокирующий режим через `ioctlsocket(FIONBIO)`.
- Состояние клиента — `struct Client { SOCKET s; std::string out; }`: буфер накапливает
  то, что не удалось отправить сразу.
- Backpressure: если `out.size() >= MAX_OUT` (1 MiB), сокет не ставится в `readfds` —
  чтение приостановлено, пока не разгрузится очередь отправки.
- Слушающий сокет добавляется в `readfds` только при `clients.size() + 1 < FD_SETSIZE`.
- `flush_out()` возвращает `false` только на фатальной ошибке; `WSAEWOULDBLOCK` — не ошибка.
- `WSAECONNRESET` / `WSAECONNABORTED` → клиент удаляется без сообщения об ошибке.
- `SO_EXCLUSIVEADDRUSE` защищает порт от перехвата другим процессом.

Ограничение модели: линейное сканирование наборов и жёсткий лимит `FD_SETSIZE`.

## 03-echo-thread-per-client

Классическая схема «поток на подключение».

- Главный поток только принимает соединения и создаёт `std::thread(client_thread, ...)`.
- `send_all()` гарантирует полную отправку принятого блока.
- Логирование через `log_line()` под `std::mutex` — вывод потоков не перемешивается.
- Счётчик активных клиентов — `std::atomic<int> g_active`.
- Исключение при создании потока перехватывается, сокет закрывается.
- Потоки складываются в `std::vector` и присоединяются после выхода из `accept`-цикла.

Ограничения: отдельный стек (~1 MiB) на клиента, переключения контекста;
вектор `threads` растёт неограниченно — завершённые потоки из него не удаляются.

## 04-echo-iocp

Асинхронная модель на порту завершения ввода-вывода.

- Порт создаётся через `CreateIoCompletionPort(INVALID_HANDLE_VALUE, ...)`,
  каждый принятый сокет привязывается к нему с `Conn*` в роли completion key.
- `struct Conn` хранит сокет, буфер 4096 байт, `WSABUF`, `OVERLAPPED`,
  состояние (`Recv` / `Send`) и счётчики `sendTotal` / `sendSent`.
- 4 рабочих потока крутят `GetQueuedCompletionStatus(INFINITE)`.
- Конечный автомат: завершился `Recv` → `startSend()`; завершился `Send` →
  при неполной отправке повторный `postSend()`, иначе новый `postRecv()`.
- `bytes == 0` → клиент закрыл соединение, ресурсы освобождаются
- Ошибки `WSARecv`/`WSASend`, отличные от `WSA_IO_PENDING`, закрывают соединение.
- `accept`-цикл различает восстановимые (`WSAECONNRESET`, `WSAECONNABORTED`, `WSAEINTR`),
  временные (`WSAEMFILE`, `WSAENOBUFS` — пауза 10 мс) и фатальные ошибки.

Ограничения текущей версии: нет graceful shutdown (рабочие потоки детачатся,
`accept` блокируется навсегда); используется синхронный `accept`, а не `AcceptEx`;
буфер на соединение фиксированный.

## 05-echo-iocp-acceptex

Тот же IOCP, но приём соединений тоже асинхронный.

- `AcceptEx` и `GetAcceptExSockaddrs` загружаются через
  `WSAIoctl(SIO_GET_EXTENSION_FUNCTION_POINTER)` с GUID-ами
  `WSAID_ACCEPTEX` / `WSAID_GETACCEPTEXSOCKADDRS`.
- Слушающий сокет тоже привязан к порту завершения; синхронного
  `accept()` в коде больше нет.
- Заранее выставлено `BACKLOG_POSTED = 32` операций `AcceptEx`;
  каждая держит свой `AcceptCtx` с готовым сокетом и буфером адресов.
- `enum class Op { Recv, Send, Accept }` — тип операции определяется
  по `IoCtx`, извлечённому из `OVERLAPPED*` через `CONTAINING_RECORD`.
- Accept-завершения различаются по `Op::Accept` в `IoCtx`,
  соединения — по completion key (`Conn*`), переданному при привязке.
- Клиентский сокет создаётся заранее в `postAccept()` с
  `WSA_FLAG_OVERLAPPED`, `AcceptEx` получает уже готовый дескриптор.
- Размеры адресных буферов — `sizeof(sockaddr_in) + 16` на каждый конец,
  как требует `AcceptEx`; общий буфер `ACCEPTBUF` без данных payload
  (`dwReceiveDataLength = 0`, чтобы не ждать первый байт).
- После завершения обязателен `setsockopt(SO_UPDATE_ACCEPT_CONTEXT)` —
  без него новый сокет не наследует свойства слушающего и
  `getpeername()` / `shutdown()` отдают ошибку.
- Адреса разбираются через `GetAcceptExSockaddrs`, затем
  `inet_ntop` + `ntohs` для вывода `ip:port`.
- `AcceptCtx` переиспользуется: после обработки сразу
  новый `postAccept()`, счётчик висящих операций остаётся постоянным.
- `DWORD flags` вынесен полем в `Conn` — `WSARecv` принимает `lpFlags`
  как in/out и может писать туда в момент завершения, локальная
  переменная к тому времени уже мертва.
- Владение сокетом передаётся в `Conn` (`c->s = sc; sc = INVALID_SOCKET;`),
  дальше вся работа только через `c->s`, чтобы не закрыть дескриптор дважды.

Что даёт по сравнению с 04: приём соединений не занимает поток,
всплеск подключений разбирается пулом воркеров, а не одним
блокирующим `accept()`; сокеты под клиентов готовы заранее.

Ограничения текущей версии: graceful shutdown по-прежнему нет
(воркеры не завершаются, освобождение ресурсов — на ОС);
буфер на соединение фиксированный; счётчик ссылок на `Conn`
отсутствует, поэтому одновременные Recv/Send на одном соединении
не поддерживаются.

## 06-echo-refcount

Та же схема IOCP + `AcceptEx`, но время жизни `Conn` управляется счётчиком ссылок.
Это снимает главную проблему 05: кто и когда имеет право вызвать `delete`.

- `std::atomic<long> ref` в `Conn`; `addRef()` перед каждым `postRecv`/`postSend`,
  `release()` в воркере **всегда** после обработки пакета — на каждую выставленную
  операцию ровно одно завершение, значит ровно один `release`.
- Начальное значение `ref = 1` — это ссылка «соединение живо», ею владеет сервер,
  а не конкретная операция.
- Если `WSARecv`/`WSASend` вернул ошибку, отличную от `WSA_IO_PENDING`, пакета в IOCP
  не будет — `release()` вызывается сразу на месте, а владелец закрывает соединение.
- `closeConn()` идемпотентен: `closing.exchange(true)` гарантирует, что снятие
  «ссылки жизни» произойдёт один раз даже при гонке двух воркеров.
- `CancelIoEx` + `shutdown` заставляют висящие операции вернуться с ошибкой или
  нулём байт, их завершения доснимают свои ссылки — `delete` происходит в тот
  момент, когда `ref` падает до нуля, и только там.
- `std::atomic<long> g_liveConns` и `g_nextId` — диагностика: по логу видно, что  число живых соединений возвращается к нулю после отключения клиентов, то есть
  утечки и двойного удаления нет.
- Теперь корректны схемы, где на одном соединении одновременно висят Recv и Send:
  объект не исчезнет из-под второй операции.

Ограничения текущей версии: graceful shutdown всё ещё отсутствует — воркеры
крутят бесконечный цикл, `t.join()` не возвращается, поэтому `closesocket` /
`CloseHandle` / `WSACleanup` в конце `main` недостижимы; `AcceptCtx` и их сокеты
не освобождаются (вектор `accepts` только хранит указатели); `shutdown(SD_BOTH)`
рубит и недоотправленные данные. Всё это закрывается в `07-echo-iocp-server`.


## 07-echo-iocp-server

Финальная версия: IOCP + AcceptEx + refcount + graceful shutdown
+ idle timeout + статистика. Устраняет все ограничения предыдущих проектов.

### Новое по сравнению с 06

- Graceful shutdown: по Ctrl+C / Ctrl+Break устанавливается g_stop,
  закрывается слушающий сокет, все живые соединения закрываются через
  closeConn(), воркерам отправляются NULL-пакеты
  (PostQueuedCompletionStatus с lp = NULL) — цикл worker завершается
  штатно, t.join() отрабатывает.
- Idle timeout (IDLE_TIMEOUT_MS = 60 000 мс): поток reaper раз в секунду
  проверяет lastAct каждого Conn; соединения без активности дольше порога
  закрываются через closeConn().
- Drain timeout (DRAIN_TIMEOUT_MS = 5 000 мс): после сигнала остановки
  main ждёт опустошения g_liveConns и g_acceptsInFlyght не дольше 5 с,
  затем принудительно завершает.
- Per-thread статистика: каждый поток ведёт thread_local Stats (выровненный
  по 64 байтам во избежание false sharing); функция aggregate() суммирует
  все срезы. Поля: accepts, recvOps, sendOps, bytesIn, bytesOut, closes, errors.
- Поток monitor: каждые 2 с выводит live/peak соединений, acc/s, MB/s in/out,
  recvOps, sendOps, closes, errors.
- Итоговая сводка: после join всех потоков печатается финальный aggregate() —
  totals: accepts, recv, send, in/out байт, closes, errors, peak.
- TCP_NODELAY на каждом принятом сокете.
- BACKLOG_POSTED = 64 одновременных AcceptEx-операций.

### Параметры (compile-time)

| Константа        | Значение | Описание                             |
|------------------|----------|--------------------------------------|
| PORT             | 5555     | Порт прослушивания                   |
| BACKLOG_POSTED   | 64       | Количество pending AcceptEx          |
| RECV_BUF         | 4096     | Размер буфера приёма (байт)          |
| IDLE_TIMEOUT_MS  | 60 000   | Таймаут простоя (мс)                 |
| DRAIN_TIMEOUT_MS | 5 000    | Таймаут drain при shutdown (мс)      |
| VERBOSE          | false    | Подробное логирование на соединение  |

### Архитектура потоков

    main()
     ├── worker x (hw_concurrency x 2)  -- IOCP-цикл (Accept / Recv / Send)
     ├── monitor                        -- вывод статистики каждые 2 с
     └── reaper                         -- закрытие idle-соединений каждые 1 с

### Жизненный цикл соединения

    postAccept() -> AcceptEx -> onAccept()
        -> CreateIoCompletionPort (attach Conn)
        -> postRecv()
            -> Op::Recv -> startSend() -> postSend()
            -> Op::Send -> postSend() (частичная) | postRecv() (полная)
        -> bytes == 0 / ошибка -> closeConn() -> release() -> delete (ref == 0)

## 08-length-prefixed-protocol

Вся инфраструктура из 07 (IOCP + AcceptEx + refcount + graceful shutdown + idle timeout +
статистика) остаётся без изменений. Новое — сервер перестаёт быть «эхом байтов» и начинает
говорить на собственном протоколе поверх TCP.

### Зачем

TCP — поток байтов, а не сообщений. Один send() на клиенте не равен одному recv() на сервере:
данные склеиваются (два сообщения в одном чтении) и рвутся (одно сообщение в двух чтениях).
Во всех предыдущих проектах это не было видно, потому что эхо возвращало ровно то, что пришло,
и граница сообщения не имела значения. Как только у сообщения появляется смысл — нужен framing.

### Формат кадра
```
+----------------+---------------------+
| uint32 BE len  | payload (len байт)  |
+----------------+---------------------+
```

- `len` — длина **только payload**, без самого префикса.
- Порядок байт — big-endian (network byte order), через `htonl` / `ntohl`.
- `len == 0` — валидный пустой кадр, ответ состоит из одного префикса.
- Сервер отвечает тем же кадром (echo на уровне сообщений, а не байтов).

### Разбор входящего потока

- У каждого `Conn` есть накопительный буфер `inbuf`; прочитанное из `WSARecv` дописывается в конец.
- `on_data()` крутит цикл: пока в буфере есть хотя бы 4 байта заголовка **и** `len` байт payload —
  кадр извлекается и обрабатывается. Это разбирает несколько сообщений из одного `recv`.
- Неполный «хвост» остаётся в буфере до следующего завершения `Op::Recv`.
- Обработанный префикс буфера срезается через `erase(begin, begin + offset)`.

### Защита от мусора и атак

- `MAX_PAYLOAD` — максимальный размер одного кадра. Клиент, приславший больший `len`,
  закрывается немедленно: иначе одно число в заголовке заставляет сервер выделить гигабайты.
- `MAX_INBUF` — потолок накопительного буфера. Защита от клиента, который шлёт байт за байтом
  и никогда не завершает кадр.
- Любая протокольная ошибка -> `LOGV("protocol error -> close")` -> `closeConn()` + `release()`.
  Протокольная ошибка не отличается по обработке от сетевой: соединение просто умирает.

### Пайплайн ввода-вывода

Модель строго полудуплексная — на соединении в каждый момент висит **одна** операция:
```
Op::Recv -> on_data() (разбор кадров, сборка ответа в outbuf) -> startSend()
Op::Send -> postSend() (неполная отправка) | postRecv() (отправлено целиком)
```

Поэтому `outbuf` не требует блокировки: в него пишет только тот поток, который сейчас
обрабатывает завершение `Recv`, и до окончания отправки новых чтений не будет.

### Параметры (compile-time)

| Константа | Значение | Описание |
|---|---|---|
| `MAX_PAYLOAD` | 1 MiB | Максимальный размер одного кадра |
| `MAX_INBUF` | 2 MiB | Потолок накопительного буфера приёма |

Остальные константы — `PORT`, `BACKLOG_POSTED`, `RECV_BUF`, `IDLE_TIMEOUT_MS`,
`DRAIN_TIMEOUT_MS`, `VERBOSE` — те же, что в 07.

### Ограничения текущей версии

- `inbuf.erase()` сдвигает остаток буфера на каждый разобранный кадр — O(n) на сообщение.
  Для потока мелких кадров это заметно; следующий шаг — кольцевой буфер или курсор `consumed`
  вместо физического сдвига.
- Нет типа сообщения: заголовок несёт только длину. Полноценный протокол добавил бы
  `[len][type][seq]`.
- Полудуплекс: пока идёт отправка ответа, новые данные от клиента не вычитываются.

## Запуск

Сначала сервер, затем клиент в отдельном окне. Адрес 127.0.0.1, порт 8080
(для 04-echo-iocp -- 9000, для 05-07 -- 5555).

Проверка без клиента, из PowerShell (порт подставьте из таблицы):

    $c = New-Object Net.Sockets.TcpClient('127.0.0.1', 8080)
    $s = $c.GetStream()
    $b = [Text.Encoding]::ASCII.GetBytes("hello`n")
    $s.Write($b, 0, $b.Length)

## Структура
Каждый каталог -- независимый проект. Код намеренно не выносится в общую библиотеку: цель -- видеть полный цикл работы с 
сокетами в одном файле и сравнивать модели напрямую.
